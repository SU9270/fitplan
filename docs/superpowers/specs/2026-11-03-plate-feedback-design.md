# 第三阶段「搭盘子与缺口反馈」设计

日期：2026-11-03　状态：实施中　依据：需求文档 v2.1 §3.3、§3.4、§9.1 第 4 阶段

## 1. 目标

核心闭环的后半段：用户把想吃的加进某一餐后，App 告诉他**这一餐**还缺什么，并给出最多 3 条可以一键应用的调整建议，由他自己决定要不要调。

### 本阶段范围

- 每一餐显示为四格「盘子」：蛋白质、主食、蔬菜、其他
- 餐级目标：全天目标按比例分到各餐，比例可以在「我的 → 设置」里改
- 缺口反馈：这一餐有记录后才显示；与餐级目标相差 ±10% 以内算达标
- 调整建议：最多 3 条，一键应用（加一样，或把某一样减半）
- 语气中立：不评价食物，不用「超标」红色警告（今日页的「已超出」一并改掉）

### 范围外（后续 PR 或阶段）

- 记录效率：最近吃过 / 常吃、复制昨天、保存为我的餐、只填营养的快速添加（下一个 PR）
- 忌口、过敏、可用设备（灵感库阶段加进问卷，届时建议遵守这些条件）
- 整道菜拆成食材分格（灵感库的菜由食材组成，届时按食材分格）
- 从灵感库挑选建议

## 2. 四格归类（`packages/core`：`plateSlot`）

按顺序判断，先命中的生效：

1. USDA 分类为 `Vegetables and Vegetable Products` → **蔬菜**
2. USDA 分类为水果、饮品（含酒精饮品）、甜食、零食、油脂、调味料、汤与酱汁 → **其他**
3. 蛋白质提供的热量 ≥ 30% → **蛋白质**
4. 碳水提供的热量多于脂肪 → **主食**
5. 其余 → **其他**

热量按 4 / 4 / 9 kcal/g 计算。没有分类的食物（自定义食物、导入分类之前记的记录）只走第 3–5 步。营养数据缺失时按 0 计算。

**与需求文档的差异**：文档 §3.4 的规则是「哪种营养素提供的热量最多就归哪一格」（标为【建议】）。按这条规则，鸡蛋（蛋白质供能 34%、脂肪 61%）、豆腐、三文鱼、牛肉末都会进「其他」，所以改为蛋白质供能达到 30% 就归「蛋白质」。阈值定义在 `constants.ts`。

整道菜（如餐馆的宫保鸡丁）按上面的规则整体归入一格；拆分到各格留给灵感库阶段。

## 3. 餐级目标（`mealTargets`）

- 默认比例：早 25%、午 30%、晚 30%、加餐 15%（需求文档 §10 第 8 条的建议值）
- 每一餐的目标 = 全天目标 × 比例，热量和三大营养素各自取整
- 用户在「我的 → 设置」里修改：每档 5%，单餐 0–100%，四餐合计必须是 100%
- 存在 `profiles` 表的四个新列里；修改比例不生成新的目标版本（不影响全天目标）

## 4. 缺口反馈（`mealGap`）

这一餐至少有一条记录才计算。热量、蛋白质、碳水、脂肪分别与餐级目标比较：

| 状态 | 条件 | 文案示例 |
|---|---|---|
| 不足 | 少于目标的 90% | 蛋白质还差 25 克 |
| 达标 | 90%–110% | 主食已够 |
| 偏多 | 多于目标的 110% | 热量比这餐目标多 120 千卡 |

- 碳水在文案里叫「主食」，与盘子的格子对应
- 午餐和晚餐还没有蔬菜时，提示「这餐还没有蔬菜」（早餐和加餐不提示）
- 文案中性，灰色，不用红色；全天的「已超出」改为「比目标多 … 千卡」
- 达标范围 ±10% 定义在 `constants.ts`

## 5. 调整建议（`suggestAdjustments`）

纯函数，输入这一餐的目标、记录和候选食物，最多输出 3 条，按以下顺序生成，够 3 条为止：

1. **蛋白质不足** → 加一份候选蛋白质食物
2. **热量偏多** → 把这一餐里热量最高的「主食」或「其他」记录减半（如「米饭减半」）
3. **主食不足**（且热量没有偏多）→ 加一份候选主食
4. **午餐 / 晚餐没有蔬菜** → 加一份候选蔬菜

**加一样**：对每个候选食物，用它的第一个份量（如「1 large」）算出需要几份才能补上缺口，按 0.5 份取整，限定在 0.5–3 份之间。选得分最好的：补上的量与缺口越接近越好；不是整数份、加完后热量超过餐级目标 110% 都要扣分。同样的得分按食物 id 排序，保证结果稳定。已经在这一餐里的食物不再推荐。

**减半**：按份量记的取 0.5 份的整数倍，按克记的取 5 克的整数倍；减不动（已经是最小值）就不推荐。

**候选食物**：中文名对照表里新增 `suggest` 列，人工标出适合「直接加进一餐」的常见熟食和即食食物（如水煮蛋、烤鸡胸、希腊酸奶、米饭、全麦面包、西兰花），排除生肉、干米、调味料等。导入时存进 `foods.suggestable`。

**一键应用**：「加一样」直接新增一条记录；「减半」修改那条记录的份量。应用后重新读取当天的数据。

所有参数（0.5 份步长、最多 3 份、最多 3 条、5 克步长、扣分权重）定义在 `constants.ts`。

## 6. 数据与接口

| 变更 | 说明 |
|---|---|
| `foods.category` | USDA 分类名（导入时从 `food_category.csv` 读取）；自定义食物为 NULL |
| `foods.suggestable` | 是否可作为建议候选，默认 0 |
| `diary_entries.food_category` | 记录时的分类快照，与营养快照一样不随食物库改变 |
| `profiles.meal_share_*` | 四餐比例（百分比整数），默认 25 / 30 / 30 / 15 |

都用 `ALTER TABLE … ADD COLUMN` 加列，不重建表；比例的合法性由 Zod 校验（合计 100，每档 5%），不加 CHECK 约束，因为在 SQLite 里给已有表加 CHECK 需要重建表。

- `GET /api/diary?date=` 增加 `mealShares` 和 `meals`：每餐的目标、合计、缺口、建议；每条记录增加 `slot`
- `GET /api/foods/:id` 增加 `slot`（详情页显示「归入：蛋白质」）
- `PATCH /api/me/settings` 增加 `mealShares`
- 加了新列以后要**重新运行一次 `food:import`**，USDA 食物才会有分类和建议标记；`pnpm dev` 发现缺分类时会提示

## 7. 页面

- **今日 · 每餐卡片**：标题旁显示「612 / 864 千卡」；2 × 2 的盘子，每格一种颜色（蛋白质天蓝、主食黄、蔬菜青柠、其他紫），格子里列出记录（点击可编辑）；下面是缺口反馈和最多 3 条建议，每条一个「应用」按钮；最后是「+ 添加」
- **食物详情**：显示「归入：蛋白质」
- **我的 → 设置**：四餐比例，每餐一组 − / + 按钮（每次 5%），显示合计，合计不是 100% 时不能保存

## 8. 测试

- core：四格归类（鸡蛋、豆腐、米饭、西兰花、苹果、橄榄油、花生酱、未分类自定义食物、营养缺失）、餐级目标取整、缺口三种状态与边界（正好 90% 和 110%）、建议的顺序与上限、份量取整、减半的下限、已在餐里的食物不推荐、结果稳定
- api：分类导入、`meals` 结构、建议只来自候选食物、修改比例的校验与保存、记录里的分类快照
- mobile：比例编辑的合计校验、建议文案拼接
