# 第三阶段「搭盘子与缺口反馈」设计

日期：2026-11-03　状态：已实施（2026-11-03 用真实 SR Legacy 数据验证）　依据：需求文档 v2.1 §3.3、§3.4、§9.1 第 4 阶段

## 1. 目标

核心闭环的后半段：用户把想吃的加进某一餐后，App 告诉他**这一餐**还缺什么，并给出最多 3 条可以一键应用的调整建议，由他自己决定要不要调。

### 本阶段范围

- 每一餐显示为四格「盘子」：蛋白质、主食、蔬菜、其他
- 餐级目标：全天目标按比例分到各餐，比例可以在「我的 → 设置」里改
- 缺口反馈：这一餐有记录后才显示；与餐级目标相差 ±10% 以内算达标
- 调整建议：最多 3 条，一键应用（加一样，或把某一样减半）
- 语气中立：不评价食物，不用「超标」红色警告（今日页的「已超出」一并改掉）

### 范围外（后续 PR 或阶段）

- 记录效率：最近吃过 / 常吃、复制昨天、保存为我的餐、只填营养的快速添加（下一个 PR）
- 忌口、过敏、可用设备（灵感库阶段加进问卷，届时建议遵守这些条件）
- 整道菜拆成食材分格（灵感库的菜由食材组成，届时按食材分格）
- 从灵感库挑选建议

## 2. 四格归类（`packages/core`：`plateSlot`）

按顺序判断，先命中的生效：

1. USDA 分类为 `Vegetables and Vegetable Products`，且每 100 克少于 70 千卡 → **蔬菜**（每 100 克 ≥ 70 千卡的是淀粉类：土豆、红薯、玉米、芋头、豌豆，按中国人的饮食习惯算主食，继续往下按营养素判断；毛豆因此归蛋白质。大蒜、生姜也会落到主食，但用量很小）
2. USDA 分类为水果、饮品（含酒精饮品）、甜食、零食、油脂、调味料、汤与酱汁 → **其他**
3. 蛋白质提供的热量 ≥ 30% → **蛋白质**
4. 碳水提供的热量多于脂肪 → **主食**
5. 其余 → **其他**

热量按 4 / 4 / 9 kcal/g 计算。没有分类的食物（自定义食物、导入分类之前记的记录）只走第 3–5 步。营养数据缺失时按 0 计算。

**与需求文档的差异**：文档 §3.4 的规则是「哪种营养素提供的热量最多就归哪一格」（标为【建议】）。按这条规则，鸡蛋（蛋白质供能 34%、脂肪 61%）、豆腐、三文鱼、牛肉末都会进「其他」，所以改为蛋白质供能达到 30% 就归「蛋白质」。阈值定义在 `constants.ts`。

整道菜（如餐馆的宫保鸡丁）按上面的规则整体归入一格；拆分到各格留给灵感库阶段。

## 3. 餐级目标（`mealTargets`）

- 默认比例：早 25%、午 30%、晚 30%、加餐 15%（需求文档 §10 第 8 条的建议值）
- 每一餐的目标 = 全天目标 × 比例，热量和三大营养素各自取整
- 用户在「我的 → 设置」里修改：每档 5%，单餐 0–100%，四餐合计必须是 100%
- 存在 `profiles` 表的四个新列里；修改比例不生成新的目标版本（不影响全天目标）

## 4. 缺口反馈（`mealGap`）

这一餐至少有一条记录才计算。热量、蛋白质、碳水、脂肪分别与餐级目标比较（2026-11-03 起早餐和加餐只比较热量和蛋白质，见下）：

| 状态 | 条件 | 文案示例 |
|---|---|---|
| 不足 | 少于目标的 90% | 蛋白质还差 25 克 |
| 达标 | 90%–110% | 主食已够 |
| 偏多 | 多于目标的 110% | 热量比这餐目标多 120 千卡 |

- 碳水在文案里叫「主食」，与盘子的格子对应
- 午餐和晚餐还没有蔬菜时，提示「这餐还没有蔬菜」（早餐和加餐不提示）
- **早餐和加餐只看热量和蛋白质**（2026-11-03，与需求文档 §3.3「每餐比较四项」不同）：很多人早餐不吃主食（鸡蛋、酸奶），按比例分到早餐的碳水（如 130 克）会让每个这样的早餐都被提示「主食还差」，还会建议「加 3 碗米饭」。碳水和脂肪由全天汇总体现，早餐少的部分午餐晚餐自然补上。规则在 `constants.ts` 的 `MEAL_GAP_NUTRIENTS`
- 文案中性，灰色，不用红色；全天的「已超出」改为「比目标多 … 千卡」
- 达标范围 ±10% 定义在 `constants.ts`

## 5. 调整建议（`suggestAdjustments`）

纯函数，输入这一餐的目标、记录和候选食物，最多输出 3 条，按以下顺序生成，够 3 条为止：

1. **蛋白质不足** → 先看这一餐「蛋白质」格里已有的食物：最多再加 1 份就能补上（如「水煮蛋 加到 3 × 1 large」），就建议加量；否则加一份候选蛋白质食物
2. **热量偏多** → 把这一餐里热量最高的「主食」或「其他」记录减半（如「白米饭 减到 1.5 × 1 cup」）
3. **主食不足**（且热量没有偏多）→ 同第 1 条：先建议给已有的主食加量（如「白米饭 加到 1.5 × 1 cup」），不行再加一份候选主食
4. **午餐 / 晚餐没有蔬菜** → 加一份候选蔬菜：选份量最接近 100 克的（一份配菜的量；按热量最低选的话永远是生菜）

**加一样**：对每个候选食物，用对照表指定的份量（如水煮蛋「1 large」）算出需要几份才能补上缺口，按 0.5 份取整，限定在 0.5–3 份之间。选得分最好的：补上的量与缺口越接近越好；不是整数份、加完后热量超过餐级目标 110% 都要扣分。同样的得分按食物 id 排序，保证结果稳定。已经在这一餐里的食物不再推荐。

**加量**：优先改用户已经选的食物，而不是推荐新的（需求文档「加一样、换一样、改份量」；用真实数据试过，午餐吃米饭、主食不够时，原来会建议「加一杯燕麦粥」）。加量至少半份、最多 1 份；按克记的最多加到原来的两倍。

**减半**：按份量记的取 0.5 份的整数倍，按克记的取 5 克的整数倍；减不动（已经是最小值）就不推荐。

**早餐和加餐的候选**（2026-11-03）：只从乳蛋、早餐谷物、烘焙（面包）、豆类、水果、坚果这几个 USDA 分类里挑（`LIGHT_MEAL_CATEGORIES`），不会建议米饭、肉、鱼。

**候选食物**：中文名对照表里新增 `suggest_portion` 列，人工标出适合「直接加进一餐」的常见熟食和即食食物（如水煮蛋、烤鸡胸、希腊酸奶、米饭、全麦面包、西兰花），并写明用哪个份量（USDA 的第一个份量常常不自然，比如水煮蛋是「1 cup, chopped」）；排除生肉、干米、调味料、蛋白粉等。导入时按份量文字找到份量，存进 `foods.suggest_portion_id`；找不到时导入报错。

**一键应用**：「加一样」直接新增一条记录；「加量」和「减半」修改那条记录的份量。应用后重新读取当天的数据。

所有参数（0.5 份步长、新食物最多 2 份（2026-11-03 由 3 份改为 2 份）、加量最多 1 份、最多 3 条、5 克步长、扣分权重）定义在 `constants.ts`。

## 6. 数据与接口

| 变更 | 说明 |
|---|---|
| `foods.category` | USDA 分类名（导入时从 `food_category.csv` 读取）；自定义食物为 NULL |
| `foods.suggest_portion_id` | 作为建议候选时用的份量；NULL 表示不作为候选 |
| `diary_entries.food_category` | 记录时的分类快照，与营养快照一样不随食物库改变 |
| `profiles.meal_share_*` | 四餐比例（百分比整数），默认 25 / 30 / 30 / 15 |

都用 `ALTER TABLE … ADD COLUMN` 加列，不重建表；比例的合法性由 Zod 校验（合计 100，每档 5%），不加 CHECK 约束，因为在 SQLite 里给已有表加 CHECK 需要重建表。

- `GET /api/diary?date=` 增加 `mealShares` 和 `meals`：每餐的目标、合计、缺口、建议；每条记录增加 `slot`
- `GET /api/foods/:id` 增加 `slot`（详情页显示「归入：蛋白质」）
- `PATCH /api/me/settings` 增加 `mealShares`
- 加了新列以后要**重新运行一次 `food:import`**，USDA 食物才会有分类和建议标记；`pnpm dev` 发现缺分类时会提示

## 9. 变更（2026-11-22）：反馈从每餐改成全天

负责人的反馈：不想每一餐都被提醒还差蛋白质、碳水、脂肪，因为每个人怎么把一天分到各餐并不一样；到最后给一个总的提醒就够了。第 3–5 节和第 7 节里「每餐」的做法由本节取代；四格归类（第 2 节）不变。

### 考虑过的做法

1. **保留每餐反馈，让用户自己调各餐比例**（原来就有这个设置）。否决：用户要先想清楚自己每餐吃多少比例，再去设置，才能让提醒变得合理；大多数人不会去调，提醒照样对不上。
2. **全天反馈，一直显示在页面上**。否决：早上刚记一个鸡蛋就看到「全天还差：蛋白质 · 碳水 · 脂肪 · 蔬菜」，等于换了个地方继续提醒，而且圆环和三格数字已经在显示进度。
3. **全天反馈，晚餐有记录之后才出现**（采用）。App 不知道用户哪一刻算「吃完了」，用「晚餐里记了东西」当作一天到了最后的信号。代价是提醒有时偏晚，只能靠加餐补；以后如果想更早看到，把 `DAY_FEEDBACK_AFTER_MEAL` 改成午餐即可。

### 规则

- **比较对象**：全天已吃的合计对每日目标，热量、蛋白质、碳水、脂肪四项都比，容差仍是 ±10%（`dayGap`）。原来「早餐和加餐只比热量和蛋白质」（`MEAL_GAP_NUTRIENTS`）的规则不再需要，已删除：早餐少吃的碳水自然留给后面几餐。
- **什么时候出现**：有每日目标，并且晚餐至少有一条记录（`DAY_FEEDBACK_AFTER_MEAL`）。看以前的日子时规则相同。
- **蔬菜**：全天任何一餐有蔬菜就不提示；原来只在午餐、晚餐各提示一次（`VEGETABLE_HINT_MEALS`，已删除）。
- **建议**（`suggestDayAdjustments`）：顺序和数量不变（蛋白质 → 热量偏多则减半 / 否则碳水 → 蔬菜，最多 3 条，每条最多 2 份），区别是：
  - 按全天的缺口算，要补的量也是全天还差的量
  - 建议都落在**一餐**里：App 请求时带上当前时间对应的那一餐（`GET /api/diary?date=&meal=`，服务器不知道用户的时区和时间）；看以前的日子时不带，服务器用晚餐
  - 只改这一餐里已有的记录（「再加一个鸡蛋」「米饭减半」），不回头改前面几餐
  - 这一餐是早餐或加餐时，只推荐 `LIGHT_MEAL_CATEGORIES` 里的食物，所以不会推荐蔬菜；晚上九点以后算加餐，推荐的就是酸奶、鸡蛋、面包这类
- **餐级目标**不再使用：接口不再返回每餐的目标和 `mealShares`，每餐标题旁只写这餐吃了多少千卡。`mealTargets`、四餐比例的设置接口和数据库列都保留，「我的 → 设置」里的入口隐藏，方便以后恢复。

### 接口

- `GET /api/diary`：`meals` 每项只有 `meal` 和 `totals`；新增 `feedback`（没有目标或晚餐没记录时为 `null`），内容是 `gap`（四项）、`hasVegetables`、`meal`（建议落在哪一餐）、`suggestions`
- 查询参数新增可选的 `meal`

### 页面

- **每餐卡片**：只有食物列表；「+ 添加」和「存为我的餐」排成一行（「存为我的餐」原来藏在展开的建议里）
- **全天反馈**：今日页最下面单独一张卡片，默认一行「全天还差：蛋白质 · 碳水」加「看建议」；点开是带数字的标签和建议，建议标题写明记在哪一餐（「可以这样调（记在晚餐）」）。都达标时写「全天已吃够」
- 文案用「全天」而不是「今天」，因为看以前的日子时也显示；「主食还差 X 克碳水」改成「碳水还差 X 克」，和页面上方三格的叫法一致
- 圆环下面「还可以吃 X 千卡 / 比目标多 X 千卡」那一行同一天去掉了（负责人：不需要提醒还能吃多少）；这个数字现在只在展开全天反馈后才看得到

## 10. 变更（2026-11-22）：只提醒缺的，不提醒多的

负责人：今天目标达成了、蛋白质吃多了这种情况，不需要提醒。

- **全天反馈卡片**只在有东西还差时出现（四项里有「还差」，或全天没有蔬菜）；都达标或只是比目标多时整张卡片不显示。原来的「全天已吃够」「比全天目标多：蛋白质」两种总结去掉了（`feedbackSummary` 这时返回 `null`）
- **展开后的标签**：比目标多的项和达标的项合在一条「热量、碳水、脂肪已够」里，不再单独写「蛋白质比全天目标多 X 克」
- **建议**：去掉「热量偏多 → 把这一餐热量最高的主食或其他减半」。热量偏多时仍然不推荐加主食（避免越加越多），蛋白质和蔬菜的建议照旧。`Suggestion` 的 `reason` 不再有 `kcal`
- 第 9 节「圆环下面那一行……这个数字现在只在展开全天反馈后才看得到」不再成立：比目标多多少现在页面上不显示，只能从圆环和三格的数字自己看出来
