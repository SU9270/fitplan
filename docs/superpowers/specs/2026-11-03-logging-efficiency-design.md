# 记录效率设计

日期：2026-11-03　状态：实施中　依据：需求文档 v2.1 §3.5（【建议】）、§9.1 第 4 阶段、§9.2「每日记录耗时 ≤ 3 分钟」

## 1. 目标

让常吃的东西几下就能记完。需求文档列出的五项里，「自建食物（仅本人可见）」第二阶段已经做了，本次做其余四项：

1. 最近吃过 / 常吃
2. 复制昨天或某一餐
3. 保存为「我的餐」
4. 只填营养的快速添加

## 2. 最近吃过 / 常吃

- 搜索页还没输入时显示，分两组：
  - **常吃**：最近 30 天里记过至少 2 次的食物，按次数排序，最多 5 个
  - **最近**：按最后一次记录的时间排序，最多 10 个，已经在「常吃」里的不重复显示
- 每行显示名称和上次记的份量（如「1.5 × 1 cup」），右边一个「+」：**按上次的份量一键记**到当前这一餐；点名称进食物详情，可以改份量
- 只列还看得到的食物：自定义食物删掉了就不再出现；上次用的份量不在了，就按上次的克数记
- 快速添加的记录不算（它们没有对应的食物）

接口：`GET /api/diary/recent` → `{ frequent, recent }`，每项包含食物 id、名称、格子，以及上次的份量（份量 id、份量名、数量、克数）和这个份量的热量。

## 3. 复制

- `POST /api/diary/copy { fromDate, toDate, meal? }`：把 `fromDate` 的记录复制到 `toDate`；给了 `meal` 就只复制这一餐（复制到同一餐）
- 复制的是记录的**快照**（名称、每 100 g 营养、份量、克数），所以即使食物后来被修改或删除，复制出来的也和原来的记录一模一样
- 返回复制了几条；源日期没有记录时返回 0，App 提示「昨天没有记录」
- 需要已同意健康数据使用，与其他写记录的接口一致；`toDate` 同样不能晚于服务器 UTC 日期的后一天

页面：
- 今日页某一餐还是空的时，显示「复制昨天的{餐次}」
- 当天还没有任何记录时，汇总卡片下面显示「复制昨天的全部记录」

## 4. 我的餐

- 把某一餐的全部记录存成一套，起个名字（默认是前几样食物名用「+」连起来）
- 存的也是快照（与记录相同的字段），所以以后加入时不受食物修改或删除的影响
- 搜索页「我的餐」一组：点一下就把整套加进当前这一餐
- 「我的」页面列出所有「我的餐」，可以删除；本次不做改名和编辑内容（删了重存即可）

表：`meal_templates`（id、user_id、name、时间）、`meal_template_items`（id、template_id、position，以及和 `diary_entries` 相同的快照字段）。

接口：
- `GET /api/meal-templates`：列表，含每套的样数和总热量
- `POST /api/meal-templates { name, date, meal }`：把这一天这一餐存成一套；这一餐是空的返回 400
- `POST /api/meal-templates/:id/apply { date, meal }`：加进某天某餐，需要已同意
- `DELETE /api/meal-templates/:id`

## 5. 快速添加

- 不选食物，只填：名称（可选，默认显示「快速添加」）、热量（必填，0–5000 千卡）、蛋白质 / 碳水 / 脂肪（可选，不填就是未知，不当作 0）
- 存成一条记录：`food_id` 为 NULL，新列 `diary_entries.is_quick = 1`；营养按「每 100 g」存，克数记为 100，这样换算和合计的逻辑不用改
- 页面上快速添加的记录不显示份量；修改页只能换餐次或删除（要改数值就删掉重新添加）
- 归格按营养素规则；只填了热量的归「其他」

接口：`POST /api/diary/quick { date, meal, name?, kcal, proteinG?, carbsG?, fatG? }`。对快速添加的记录用 PATCH 改份量返回 400。

## 6. 范围外

「我的餐」改名和编辑内容、跨餐复制（如把昨天的晚餐复制到今天的午餐）、按星期几推荐、条码。

## 7. 测试

- api：最近 / 常吃的排序、去重、阈值，删除的食物不再出现；复制整天或单餐（快照一致）、空来源、越权、需要同意；「我的餐」的保存、列出、应用、删除、越权、空餐；快速添加的校验与未知营养素；快速添加的记录不能改份量
- mobile：份量文字、默认的「我的餐」名称、快速添加表单的校验
